## Why

We want to prove an autonomous, spec-driven migration workflow end to end
against a small, real, read-only slice of the product. The teacher dashboard
home section list is a good pilot: it is a self-contained region with a single
data dependency (`GET /api/v1/sections`), it has a clear empty state and a clear
populated state, and it exercises every capability the workflow must
demonstrate — a new `frontend/` package, a Studio route with a lazy boundary,
the typed `DashboardApiClient`, deterministic fixtures, unit/parser/component
tests, accessibility checks, and region-scoped visual parity.

The goal is the workflow, not the feature. The candidate route is preprod-only
(`FrontendStudioController#index` 404s in production) and read-only, so the
blast radius is near zero while the process value is high.

## What Changes

- A new package `frontend/packages/teacher-dashboard` (`@code-dot-org/teacher-dashboard`)
  renders a READ-ONLY teacher dashboard home region: the empty/no-sections state
  and the section-list/section-cards state, at parity with the legacy region on
  `https://test-studio.code.org/teacher_dashboard/home`.
- A new Studio route file `frontend/apps/studio/src/routes/teacher_dashboard/home.tsx`
  (canonical path `/teacher_dashboard/home`, served under the `/frontend-studio`
  basepath) that owns ONLY the route definition and a `React.lazy` +
  `<Suspense>` boundary onto the package's exported component.
- A new list method on the existing core `sections` domain
  (`frontend/packages/core/src/api/dashboard/sections/`) for `GET /api/v1/sections`,
  with a new zod schema modeling the `summarize_without_students` response
  (the existing `ConciseSectionSchema` models the different `concise_summarize`
  shape and must NOT be reused), a parser test, a react-query hook + key, and
  MSW handlers with empty-list and two-section fixtures.
- Two Playwright scenarios (empty; two-section) with region-scoped visual parity,
  scoped axe, and keyboard/focus assertions.

Consumed data is snake-cased on the wire; the schema/parser camelCases at the
boundary, matching the existing core convention.

## What Does NOT Change

- The legacy route `/teacher_dashboard/home`, its Rails controller
  (`TeacherDashboardController#show`), the legacy React entry
  (`apps/src/sites/studio/pages/teacher_dashboard/show.js`), and all
  `apps/src/templates/studioHomepages/teacherHomepageV2/` components are
  UNTOUCHED.
- No redirect is added from `/teacher_dashboard` to the candidate; the candidate
  is reached only at its own `/frontend-studio/...` URL.
- No change to `GET /api/v1/sections` server behavior, serializer, or auth.
- No wholesale import or port of `apps/src` teacher-dashboard components into the
  new package. UI is rebuilt on the design system.

## Out of Scope (verbatim)

create/edit/archive/delete sections; drag reorder/order persistence;
add-students; course-assignment flows; progress/roster/materials/settings/
assessments/stats/projects/text-responses; demo section creation; AI
differentiation/chat; promotions; Global Edition.

## Impact

- New code: `frontend/packages/teacher-dashboard/**`; one Studio route file plus
  the generated `routeTree.gen.ts` (regenerated by the Vite plugin, not
  hand-edited); a workspace dep entry in `frontend/apps/studio/package.json`;
  additive methods/schema/fixtures under
  `frontend/packages/core/src/api/dashboard/sections/` and
  `frontend/packages/core/src/api/mocks/`.
- Visual tooling: consuming region-scoped parity requires
  `@code-dot-org/playwright-support` (currently on an unmerged branch — see
  design.md Risks). This is an OPUS-owned Phase-2 prerequisite, not a Sonnet task.
- No database, no migration, no production surface (preprod-only route).
