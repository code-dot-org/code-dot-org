# Design: pegasus-db-hoc

## Context

`hoc_activity` consumers (verified 2026-07-07):

| site | op |
|---|---|
| `dashboard/engines/hoc_legacy/app/services/concerns/hoc_legacy/session_manageable.rb:43` | insert |
| `session_manageable.rb:60` | dataset (read/update) |
| `dashboard/engines/hoc_legacy/app/controllers/hoc_legacy/certificates_controller.rb:28` | update |
| `certificates_controller.rb:45` | read |
| `bin/cron/geocode_hoc_activity` | batch read + update (+ `Properties` cursor `hoc_activity.last_id`, staying on PEGASUS_DB until `pegasus-db-properties`) |
| `bin/cron/hoc_student_name_cleanup` | batch update (name scrub) |
| `aws/dms/tasks.yml` | replication (PII columns removed) |

Routes are gated by `CDO.hoc_tracking_enabled` (true in prod).
Traffic: inserts/updates on tutorial begin/finish + certificate
views; per-minute geocode cron. Both schemas share one Aurora
cluster; `CDO.pegasus_db_name` / `CDO.dashboard_db_name` give the
schema names.

## Goals / Non-Goals

**Goals:**
- `hoc_activity` in the dashboard schema; zero `PEGASUS_DB`
  references to it; zero downtime; per-step revert.

**Non-Goals:**
- ActiveRecord-ifying the access (stays Sequel on `DASHBOARD_DB`).
- Moving the `properties` cursors (that is `pegasus-db-properties`).
- Any change to tracking/certificate behavior.

## Decisions

**1. Rename + compatibility view (the series pattern).** The oneoff
does, in one connection:

```ruby
DB.run "RENAME TABLE #{peg}.hoc_activity TO #{dash}.hoc_activity"
DB.run "CREATE VIEW #{peg}.hoc_activity AS SELECT * FROM #{dash}.hoc_activity"
```

`RENAME TABLE` is atomic; the view is updatable (simple SELECT *), so
not-yet-deployed code writing `pegasus.hoc_activity` keeps working.
`--revert` drops the view and renames back. Schema names come from
`CDO.pegasus_db_name`/`CDO.dashboard_db_name`, never hardcoded
(adhoc/test envs differ).

**2. Deploy order (the runbook).**
1. Ops runs the oneoff on production (and staging/adhocs as they
   converge). Old code unaffected (view).
2. Deploy: AR migration no-ops (`table_exists?`), repointed code
   reads/writes the real table directly.
3. After the deploy settles, ops runs the oneoff's `--drop-view`
   step (separate flag, not automatic — the view must outlive the
   deploy window).
Revert at any step: `--revert` before deploy; code revert after.

**3. AR migration is create-if-absent, schema from the live table.**
`SHOW CREATE TABLE` against the local pegasus dev DB is the source of
truth for columns/indexes (the pegasus migration files 050/060/061/
074/078/141 accumulated drift). Guarded
`return if table_exists?(:hoc_activity)`. This puts the table in
`schema.rb`, which is what makes dev/test/CI work once
`pegasus/migrations` dies. Dev note: the pegasus dev schema keeps an
orphaned `hoc_activity` (still created by pegasus migrations until
`pegasus-directory-removal`); code never reads it post-repoint.

**4. RuboCop cops.** Removing the `hoc_legacy` exclusion from
`rubocop_pegasus_db_usage.rb` makes any future PEGASUS_DB reference
there an error. The sibling `rubocop_dashboard_db_usage.rb` governs
DASHBOARD_DB use — read its allowed-paths list and either add
`dashboard/engines/hoc_legacy/` or use inline disables matching house
style (whichever the cop's own docs prescribe; do not weaken the cop
globally).

**5. DMS entry moves with the table.** `dashboard.hoc_activity`
keeps the `remove_column` PII list verbatim. The Redshift location
changes (`pegasus_production_pii` → `dashboard_production_pii`);
this ships only with data-team acknowledgment (task gate). The DMS
task definition on the DATA production stack must be re-generated by
infra after merge (existing documented process:
`rake stack:data:start RAILS_ENV=production ADMIN=true`).

## Risks / Trade-offs

- **View window write anomaly:** none known — updatable view over
  SELECT * passes inserts/updates/deletes through. AUTO_INCREMENT
  lives on the base table and moves with it.
- **Geocode cron mid-rename:** the cron runs every minute; a
  statement in flight during RENAME gets a table-lock wait, not an
  error. Acceptable.
- **DMS re-load:** moving the source table means DMS full-load task
  re-copies it to the new Redshift schema. hoc_activity is large-ish
  (years of HoC events) — data team schedules the re-load; the old
  `pegasus_production_pii.hoc_activity` copy is theirs to drop.
- **Adhoc/test stacks** converge later; the view keeps stale code
  working there too. `pegasus-db-retire` sweeps any leftover views.
