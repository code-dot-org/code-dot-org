# Dashboard Secrets in Kubernetes (K8S)

## Tracing A Secret From AWS Secrets Manager To A Dashboard Kubernetes Pod

Let's say we want to fetch `staging/cdo/db_writer` from our dashboard pod (aka "container")

1. In AWS Secrets Manager we have: `staging/cdo/db_writer` ([`config.yml.erb`](../../config.yml.erb))
1. In the Kubernetes cluster, we install the [External Secrets Operator (ESO)](https://external-secrets.io/) using helm+opentofu (see: [`cluster-infra-argocd/helm.tf`](../tofu/codeai-k8s/cluster-infra-argocd/helm.tf))
1. In each Kubernetes namespace (staging/prod/levelbuilder/test/adhoc-*) we provision a namespace-scoped ESO `SecretStore` named `aws-secrets-manager-store` ([`infra/eso-per-envtype/templates/_envtype.tpl`](../tofu/codeai-k8s/cluster-infra-argocd/infra/eso-per-envtype/templates/_envtype.tpl))
1. That `SecretStore` uses a dedicated Kubernetes service account for staging, tied to AWS via IRSA. (see: [`infra/eso-per-envtype/templates/_envtype.tpl`](../tofu/codeai-k8s/cluster-infra-argocd/infra/eso-per-envtype/templates/_envtype.tpl))
1. The AWS IAM role for that service account is scoped to be able to access only AWS Secrets matching: ([`modules/eso-per-envtype/iam.tf`](../tofu/codeai-k8s/cluster-infra/infra/standard-envtypes/modules/eso-per-envtype/iam.tf))
   - `staging/cdo/*`
   - `CfnStack/staging/*`
1. OpenTofu provisions an `ExternalSecret` which configures the External Secrets Operator to periodically sync AWS secrets matching `staging/cdo/*` into Kubernetes Secret `cdo-external-secrets` (see: [`infra/eso-per-envtype/templates/_envtype.tpl`](../tofu/codeai-k8s/cluster-infra-argocd/infra/eso-per-envtype/templates/_envtype.tpl))
   - While syncing it rewrites keys to remove the `staging/cdo/` prefix from AWS Secrets Manager secret names
   - The sync refreshes every 5 minutes
1. So now we have in our Kubernetes cluster in the `staging` namespace a Kubernetes Secret `cdo-external-secrets` with 50+ child keys, one of which is `db_writer`
1. When a dashboard pod launches, its manifest specifies that Kubernetes secret `cdo-external-secrets`'s sub-keys, including `db_writer`, will be mapped onto its environment variables, each with a `CDO_` prefix. (see: [`_dashboard.yaml`](../helm/templates/dashboard/_dashboard.yaml))
1. Therefore, the `db_writer` key from `cdo-external-secrets` will be available as the `CDO_db_writer` env var inside the pod.
1. `CDO.*` in ruby reads from `CDO_*` env variables. (see: [`lib/cdo.rb`](../../lib/cdo.rb))
1. So in ruby running in the dashboard pod we now have `CDO.db_writer`.

## Local Secrets Can Override AWS Secrets Manager Secrets

This allows us to inject things like MySQL and redis credentials for adhoc or equivalent deploys.

- `cdo-local-secrets` is a Kubernetes `Secret` object with many sub-secrets (see: [`cdo-local-secrets.yaml`](../helm/templates/cdo-local-secrets.yaml))
- it is Helm-managed instead of AWS-backed
- in Skaffold local development, Helm gets those local-service values from repo-root `cdo-local-secrets.env` which is automatically generated by `k8s/bin/cdo-local-secrets`
- the dashboard pod imports it with `envFrom`
- its keys become `CDO_*` environment variables in the pod
- Dashboard makes `CDO_*` env variable available as `CDO.*` ruby objects.

### A Note On Storage And Encryption

- the source secret in AWS Secrets Manager is encrypted at rest there
- after sync, the value is also stored in a Kubernetes `Secret` object, not just transiently in process memory

## Monitoring and local development

Live deployments leave `localDev.disableExternalIntegrations: false` (the
chart default). No monitoring credentials or blank boot defaults are emitted
in that mode. Secrets Manager supplies the credentials through
`cdo-external-secrets`.

Skaffold's development values set `localDev.disableExternalIntegrations: true`.
That mode supplies the blank credentials needed for keyless boot and disables
Sentry and OpenTelemetry, even when the worker uses `RAILS_ENV=production`.
Monitoring overrides remain after external secrets in `envFrom`, so a local
cluster with synced credentials still suppresses reporting. Explicit container
`env` entries take precedence over all `envFrom` sources.

MySQL, Redis, and MinIO credentials remain controlled by their respective
`services.*.enabled` flags. They do not depend on the monitoring setting.

Live environment values must set both `require_external_secrets: true` and
`activeJobWorker.RAILS_ENV` to the target Rails environment. The worker does not
inherit the chart-wide `RAILS_ENV`; its default is `adhoc`, where Sentry is off.
Production, staging, test, and levelbuilder enable Sentry in Rails configuration.
The backend credential is `dashboard_sentry_dsn`; `sentry_dsn`, `sentry_api_key`,
and `sentry_auth_token` do not configure Rails error reporting.

Sentry initializes in Rails workers as well as web processes. Its ActiveJob
integration captures unhandled job exceptions. OpenTelemetry is not required
for error delivery. Handled errors can use `Observability::Errors.report`;
intermediate failures handled by ActiveJob `retry_on` are not reported by default.

### Upgrading an existing live deployment

After syncing the chart with local mode disabled, inspect the existing
`cdo-local-secrets` Secret for obsolete monitoring keys. Older chart versions
wrote them through `stringData`, which Kubernetes stores in `data`; omission
from the new template must not be assumed to remove those stored entries.

For the default release name, run the following in the target live namespace
(using `kubectl -n NAMESPACE`). This removes only monitoring overrides
and preserves local service passwords. It also covers a namespace previously
run with local mode enabled:

```sh
kubectl -n NAMESPACE patch secret cdo-local-secrets --type merge --patch '{
  "data": {
    "enable_sentry": null,
    "enable_opentelemetry": null,
    "dashboard_sentry_dsn": null,
    "cronjobs_honeybadger_api_key": null,
    "dashboard_honeybadger_api_key": null,
    "pagerduty_token": null,
    "sentry_api_key": null,
    "sentry_auth_token": null,
    "sentry_dsn": null,
    "slack_bot_token": null,
    "slack_endpoint": null,
    "slack_start_build_token": null,
    "slack_token": null
  }
}'
kubectl -n NAMESPACE rollout restart deployment/cdo-active-job-worker
kubectl -n NAMESPACE rollout status deployment/cdo-active-job-worker
```

Restart any other consumers of that Secret as well. Environment variables are
read when containers start. Verify that the new worker has a nonblank
`CDO.dashboard_sentry_dsn`, Sentry is initialized, and a controlled failing
ActiveJob reaches Sentry in staging before rolling out to production. Check
credential presence without printing credential values.
