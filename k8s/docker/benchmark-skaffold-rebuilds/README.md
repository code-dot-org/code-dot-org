# Profiling `skaffold build`

Our basic technique is use `git log` to measure the daily odds of different cache invalidating file changes
and then make a test plan where we invalidate each `COPY` line, and measure `skaffold build` rebuild time.

NOTE: we currently only test invalidation of dockerfiles that only do `COPY` operations. It would be great
to implement a mode that tests slower rebuilds too (triggers yarn build, triggers yarn install, triggers gemfile install, etc).

## Updating `daily-odds-of-file-change-report.md`

See [daily-odds-of-file-change-report.md](/Users/seth/src/code-dot-org/k8s/docker/benchmark-skaffold-rebuilds/daily-odds-of-file-change-report.md) for the human-readable analysis of how often these copy-path inputs change from one 6am Pacific daily build to the next. Regenerate it, along with [daily-odds-of-file-change.json](/Users/seth/src/code-dot-org/k8s/docker/benchmark-skaffold-rebuilds/daily-odds-of-file-change.json), with:

```sh
bundle exec ruby update-daily-odds.rb
```

## Simulating Daily File Changes (profiling dockerfile rebuilds)

This workflow turns the historical per-path change rates into a synthetic sequence of “typical days,” then runs repeated `skaffold build` passes so you can compare how different Dockerfile layer arrangements behave under realistic cache misses.

### Generating a test plan

Generate a virtual day plan from `daily-odds-of-file-change.json` with:

```sh
bundle exec ruby generate-test-plan.rb
```

Change the number of simulated days with:

```sh
bundle exec ruby generate-test-plan.rb --test-days=20
```

The generator always uses `day: 0` as the first plan day. That entry invalidates every copy path and is marked with `"cache_miss_all_day": true`, and it counts toward `--test-days`.

### Executing the test plan

Execute the current plan with:

```sh
bundle exec ruby run-test-plan.rb \
  --description="baseline dockerfile layout"
```

To profile Dockerfile changes:

1. Set up the Dockerfiles in the first layout you want to measure.
2. Run the executor and give the run a descriptive `--description`.
3. Change the Dockerfiles to the alternate layout.
4. Run the executor again with a different `--description`.
5. Compare the resulting `test-run-<id>.json` summary files.

## Normal Usage

Regenerate the report, then generate a plan, then execute it.

## What Gets Written

Generated artifacts in this directory:

- `daily-odds-of-file-change-report.md`
- `daily-odds-of-file-change.json`
- `test-plan.json`
- `test-run-<id>/`

Each `test-run-<id>/` contains:

- `description.txt`
- `test-plan.json`
- `dockerfiles/`
  - Snapshots of the Dockerfiles referenced by `daily-odds-of-file-change.json`
- `logs/warm-cache/skaffold-build.log`
- `logs/dayN/skaffold-build.log`
- `test-run-<id>.json`

The executor restores any modified files when the run ends, even if a build fails.

## Smoke Testing

### Fast smoke test for the report

```sh
bundle exec ruby update-daily-odds.rb
bundle exec ruby generate-test-plan.rb --test-days=2
```

Verify the outputs exist:

```sh
ls daily-odds-of-file-change-report.md
ls daily-odds-of-file-change.json
ls test-plan.json
```

### Safe smoke test for the executor

This avoids running real Docker builds by putting a fake `skaffold` earlier in `PATH`.

```sh
tmpdir=$(mktemp -d)
cat > "$tmpdir/skaffold" <<'SH'
#!/bin/sh
echo fake skaffold "$@"
exit 0
SH
chmod +x "$tmpdir/skaffold"

PATH="$tmpdir:$PATH" bundle exec ruby run-test-plan.rb \
  --description="fake skaffold smoke test"
```

What to check after the fake run:

- a new `test-run-<id>/` exists
- it has `description.txt`
- it has `test-plan.json`
- it has `dockerfiles/` with the expected Dockerfile snapshots
- it has `logs/warm-cache/skaffold-build.log`
- it has one `logs/dayN/skaffold-build.log` per test day
- the summary JSON embeds the entire test plan

## Caveats

- `daily-odds-of-file-change.json` is intentionally generated by `update-daily-odds.rb`, not by `generate-test-plan.rb`
- `run-test-plan.rb` runs plain `skaffold build` from repo root
- `run-test-plan.rb` requires `--description=...` so each run is labeled on disk
- the test plan is nondeterministic; rerunning the generator will produce a different sequence of virtual days
- the main `code-dot-org.dockerfile` entry in `daily-odds-of-file-change.json` is a repo-root synthetic file intended to invalidate the final `COPY ./ ./` layer without also targeting one of the sub-Dockerfile copy paths
- if a Dockerfile stops being “copy file only,” revisit the derivation logic under `src/`
- only tests rebuilds of simplestic "COPY ONLY" dockerfiles, doing a more complete simulation that invalidates yarn build, yarn install, bundle install, etc should come later

## If Something Breaks

Start here:

- `src/derive-dependencies.rb`
  - figures out which Dockerfiles count as copy-only and which copy paths they own
- `src/generate_cache_miss_maker_json.rb`
  - chooses the synthetic file paths and writes `daily-odds-of-file-change.json`
- `src/cache_miss_test_plan_support.rb`
  - JSON loading/writing and path-collapsing helpers

If the generated Dockerfile/path maps look wrong, fix the derivation logic instead of hardcoding more paths in the top-level scripts.
