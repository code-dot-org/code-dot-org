## 1. A — the `cdo/local_development` require

Fixed, with the require inside the `aws_s3_emulated` guard rather than at the
top of the file. Two reasons, and I checked the obvious approach first:

A top-level `require 'cdo/local_development'` does work — I tried it, and both
load orders resolve — but it introduces a genuine cycle, since
`cdo/local_development` requires `cdo/aws/s3` back by way of
`s3_emulation/populator`. It resolves today only because every cross-reference
sits in a method body, which is not a property worth depending on. And
`populator` requires `httparty`, so a top-level require pulls emulation
machinery into every production process that touches S3.
`lib/cdo/app_server_hooks.rb` already requires `cdo/aws/metrics` and
`cdo/aws/ec2` from inside method bodies, so the idiom is established here.

**The regression test runs in a subprocess**, which is the part worth
explaining. Inside the suite `Cdo::LocalDevelopment` is reachable whatever
`s3.rb` does, because something else has already required it — a test written
the normal way passes against the unfixed file and proves nothing. Only a
process that loaded `s3.rb` alone can tell the difference. I verified it fails
against the unfixed file with `NameError: uninitialized constant
Cdo::LocalDevelopment` and passes with it, and added a second case that loads
the pair in both orders so the cycle cannot regress into a half-loaded module.

**One thing I want to be accurate about**: this does not change
`test_aws_s3_integration.rb`'s pass count. The affected test now proceeds far
enough to hit a request VCR has no cassette for, so it is still 1 failure and 6
errors. What changed is the composition — before, one error was the `NameError`
and the rest were VCR; now all six are `VCR::Errors::UnhandledHTTPRequestError`.
So "no AWS credentials" is finally a true account of that file, which it was
not when we were both saying it.

**Also checked and not a bug**:
`dashboard/legacy/middleware/sound_library_api.rb:34` makes the same call
without requiring the file, but Rails autoloads the constant, so it is fine. I
confirmed with `rails runner` rather than assuming either way.

## 2. The adjacent one — a test file that never ran

`lib/test/cdo/aws/s3.rb`. `lib/Rakefile:8` builds its list from
`FileList["test/**/test_*.rb"]`, and that name matches neither that pattern nor
the `*_test.rb` convention, so it has never run under `rake test`, in CI or
locally, for as long as the glob has been there. I noticed it only because it
is the test file for the code A touches.

Renamed to `test_s3.rb`. The five tests pass and cover `cached_exists_in_bucket?`
plus the cache invalidation in `upload_to_bucket` and `delete_from_bucket`,
which has no other coverage in the repository.

I verified this one through `rake test` in a single process rather than
standalone, because the file now loads alongside every other lib test for the
first time: its `setup` calls `AWS::S3.create_client`, which assigns a
module-level accessor, and it defines a top-level `BUCKET` constant. Neither
collides — `BUCKET` is unique within `test/`, and the suite goes 792 → 799
tests and 2504 → 2527 assertions, which is exactly my two files, with failures
unchanged at the two `test_optimize.rb` size assertions.

**Worth a look on your side**: if one directory's test files can silently not
match the runner's glob, others may have the same gap. I have not swept for it,
and it is outside the minimal brief, but it is the kind of thing that hides
real coverage loss.
