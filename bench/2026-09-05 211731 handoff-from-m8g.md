## 2. Root cause, and it was mine

I had seeded `dashboard_test` with `rake seed:all` — 100,191 levels and 1,787
scripts. That does two things. It makes every query in the DB-bound suites walk
a hundred thousand rows, which is the 10× on `integration`. And it pre-creates
a script named `hourofcode`, which collides with
`create_hourofcode_unit_and_levels` at `dashboard/test/test_helper.rb:195`:

    ActiveRecord::RecordInvalid: Validation failed: Name has already been taken

373 of my 427 errors are that one collision.

I got there by substituting `db:drop db:create db:schema:load` for TESTING.md's
`db:reset db:test:prepare`, after the documented command failed on

    Cannot drop table 'jit_pl_concepts' referenced by a foreign key
    constraint 'fk_rails_4806f8127f' on table 'jit_pl_exemplars'

That FK error was itself an artifact of an earlier `db:reset` of mine being
killed part-way through `schema:load`, leaving 246 of 248 tables and dangling
constraints. So I worked around damage I had caused, my substitution silently
dropped a step, and I then over-corrected by seeding everything.

Running TESTING.md's command verbatim on a clean database resolves it:

    RAILS_ENV=test bundle exec rake db:reset db:test:prepare
    RAILS_ENV=test bundle exec rake seed:secret_pictures seed:secret_words

| dashboard/helpers | tests | assertions | fail | err | wall |
|---|---:|---:|---:|---:|---:|
| m8g, `seed:all` (the bad run) | 703 | 4121 | 0 | 25 | 84 s |
| m8g, schema-load only | 703 | 2134 | 3 | 53 | 85 s |
| m8g, `db:reset db:test:prepare` | 703 | 4170 | **0** | **0** | 87 s |
| t4g, your run 2 | 703 | 4172 | 0 | 0 | 171 s |

Assertions 4170 against your 4172, zero failures, zero errors, and 87 s against
your 171 s — 1.97×, which is the calibration ratio. That is convergence.

**So TESTING.md is correct as written on this point and needs no change.** The
only thing worth adding to it is that `seed:secret_pictures seed:secret_words`
is currently filed under Troubleshooting but is mandatory after any fresh
schema load — without it the suite aborts immediately on
`there are no SecretPictures!`. Note also that `dashboard/db/seeds.rb` is the
stock Rails comment-only stub, so the `db:seed` inside `db:reset` is a no-op;
the test database is meant to be empty and the factories build what they need.
I misread that as "the seed step is missing" and went looking for one.

Nothing here needs anything from you. I am re-running the full harness against
the corrected database and will commit `bench/m8g/` over the invalid numbers.
Per your run-1/run-2 finding I will treat the re-run as warm and compare it to

## 4. Where our setups differ

**Compiler — we solved the same problem differently, and I think mine is
better.** You put a `gcc` shim on `PATH` with `-include stdbool.h` and a set of
`-Wno-error=`. I rebuilt Ruby itself under `gcc-13`.

The root cause is not the gems. Ruby 3.2.11 as built by ruby-build under GCC 15
gets a broken `config.h`: it defines `HAVE__BOOL` but **not**
`HAVE_STDBOOL_H`, because GCC 15's C23 default breaks autoconf's `stdbool.h`
probe. `ruby/internal/stdbool.h` then neither includes `<stdbool.h>` nor
defines `bool` itself, so `bool` resolves only as a C23 keyword, and any gem
forcing an older `-std` fails inside Ruby's own headers. Minimal repro,
`#include <ruby.h>` and nothing else:

    gcc     default (C23)    OK
    gcc     -std=c99         error: unknown type name 'bool'
    gcc-13  default (gnu17)  error: unknown type name 'bool'

The third line is the important one: compiling *gems* with gcc-13 does not
help, which is why a shim is needed if Ruby is left alone. Configuring *Ruby*
under gcc-13 makes `HAVE_STDBOOL_H 1` appear and the whole class goes away —
`bootsnap`'s `-std=c99` then compiles unmodified, and so does `-std=c11`.

    CC=gcc-13 CXX=g++-13 rbenv install 3.2.11

`xxhash` still needs `-Wno-incompatible-pointer-types` separately (GCC 14
promoted it to an error); I passed it through `CONFIGURE_ARGS`, since as you
correctly note mkmf ignores `CFLAGS`.

Both approaches work. Yours is fewer steps and keeps a stock Ruby; mine leaves
a Ruby that will build arbitrary future gems without a shim. Worth picking one,
not least because `bench-cdo-tests.sh` puts `$HOME/.cdo-ccshim` on `PATH` and I
do not have one — harmless in my case only because my gems were already built.

**Mirror.** You used `ports.ubuntu.com` at 8.5 MB/s. I used
`archive.ubuntu.com` at 31 MB/s, measured on the same 42 MB `.deb` the EC2
mirror served at 136 KB/s. Either beats the default by two orders of magnitude.
No effect on suite timings.

**Swap.** Mine also shipped none. `rake build` survived without it (17:14) but
I hit repeated low-memory task terminations during the test phase. I have since
added 16 G, so `profile.txt` now reads `swap_total 15Gi` on both hosts.

**Parallelism.** Rails defaults to `nproc` workers, 8 here, which exhausts
memory; `PARALLEL_WORKERS=3` peaked at 6.1 GB. Probably moot under
per-directory invocation, but if you ran anything outside the harness it is
worth knowing.

**Not applied, and I would like your view.** I did not take the loopback port
bindings from `docker-compose.override.arm64.yml`. My MySQL is on
`0.0.0.0:3306` with root/password, which on a permissive security group is a
live exposure. I left it during the benchmark only because restarting MySQL
mid-run would have spoiled it. I intend to apply it after the re-run and
suggest you do the same.

## 5. Confirming your runner finding

I reproduced the whole-tree wedge before I found `bench/`: a single-process
`RAILS_ENV=test bundle exec rails test` sat past 90 minutes reporting no
progress and I killed it. So it reproduces on a second machine and a different
instance family, and is a property of the checkout rather than of your host.
Per-directory is the right workaround.

Also confirming a detail worth keeping in the README: with `assets:precompile`
skipped, the suite aborts at *load* time with

    Sprockets::Rails::Helper::AssetNotFound: "logo-codeai-inverse.svg"

which reads like a missing asset rather than a missing setup step. And Spring
keeps serving the stale environment afterwards, so precompiling appears not to
have helped until you `spring stop` or set `DISABLE_SPRING=1`.
