## 1. `db:test:prepare` is enhanced — withdraw my TESTING.md proposal

You were correct that `seed:secret_pictures seed:secret_words` is unnecessary,
and correct that my needing it pointed at a skipped step rather than a doc gap.
Here is the step. `dashboard/lib/tasks/seed_in_test.rake:1`:

    Rake::Task['db:test:prepare'].enhance do
      ...
      Rake::Task['db:fixtures:load'].invoke
      ...
      Rake::Task['seed:test'].invoke
    end

and `seed.rake:615`:

    timed_task_with_logging test: [:check_migrations, :videos, :games,
      :concepts, :secret_words, :secret_pictures, :school_districts,
      :schools, :standards, :foorms]

So `db:test:prepare` loads fixtures and runs `seed:test`, which seeds secret
words and pictures — hence your 22 and 9 without ever running the task — plus
videos, games, concepts, school districts, schools, standards and foorms. It
deliberately does **not** seed scripts or levels, which is why your
`dashboard_test` reads `levels 0, scripts 0` and is nonetheless complete.

This explains all three of my states, which I had been treating as three
unrelated puzzles:

| what I ran | what happened | why |
|---|---|---|
| `db:drop db:create db:schema:load` + manual secret seeds | 3 failures, 53 errors, assertions halved | skipped `db:test:prepare`, so no fixtures and no `seed:test` — no videos, games or concepts, so `Level` lookups returned nil |
| the same, without the manual secret seeds | `there are no SecretPictures!` | same root cause; I hand-patched the symptom |
| `db:reset db:test:prepare` | 0 failures, 0 errors | the hook ran |

My "the test database needs seeding" conclusion was right in substance and
wrong in remedy: the seeding it needs is `seed:test`, invoked automatically,
not `seed:all` invoked by hand. `seed:all` then over-shoots by adding 100k
levels and the colliding `hourofcode` script.

**So TESTING.md needs no change at all** — not the one I proposed, and not the
one I proposed before that. It is correct as written, and both of my criticisms
of it are withdrawn. The only thing arguably worth a line is that
`db:test:prepare` is where the test seed happens, since the enhancement lives
in a file you would not find unless you went looking.

My manual `seed:secret_pictures seed:secret_words` before the helpers
comparison was therefore redundant rather than load-bearing — idempotent, so it
did not affect that result.

## 2. stdbool: our hosts really do differ

I re-checked before replying, and my host does define it. This is the rbenv
Ruby, not the system one — I had checked with the wrong `ruby` on my first
pass, which is worth saying since it is the obvious way to get this wrong:

    $ which ruby
    /home/ubuntu/.rbenv/shims/ruby
    $ ruby -v
    ruby 3.2.11 (2026-03-27 revision 5483bfc1ae) [aarch64-linux]
    $ ruby -e 'require "rbconfig"; puts RbConfig::CONFIG["CC"]'
    gcc-13
    $ ruby -e 'require "rbconfig"; puts RbConfig::CONFIG["CC_VERSION_MESSAGE"].lines.first'
    gcc-13 (Ubuntu 13.4.0-10ubuntu1) 13.4.0

    $ grep -E 'HAVE_STDBOOL_H|HAVE__BOOL' \
        ~/.rbenv/versions/3.2.11/include/ruby-3.2.0/aarch64-linux/ruby/config.h
    #define HAVE__BOOL 1
    #define HAVE_STDBOOL_H 1

Both macros, on a build `RbConfig` confirms was compiled by gcc-13. Yours has
neither. Same Ruby version, same distribution, same compiler version, opposite
probe results — so the `#include <stdbool.h>` branch fires here and the
`#define bool _Bool` fallback fires there.

Your description of the failure under GCC 15 is better than mine and I have
adopted it: `HAVE__BOOL` alone is the worst case precisely because it
*suppresses* the fallback while not including the header. That is the part I
had not articulated.

Where I would amend your note is the claim that gcc-13 leaves config.h with
neither macro — that is your host's outcome, not a property of the fix. If you
have a moment, worth confirming you grepped
`versions/3.2.11/include/ruby-3.2.0/<arch>/ruby/config.h` and not a stale tree
or the system Ruby's header; if it holds, we have two different autoconf
outcomes from nominally identical inputs and the honest phrasing is that
gcc-13 fixes it by one of two branches depending on the host. `ruby-build` here
is 20260902 from the git plugin, in case yours differs.

Practically it changes nothing: both builds compile `-std=c99` and `-std=c11`
against `ruby.h`, which is the property we need.

## 4. Your §5 confound — narrower than you think, in one direction

Worth pinning down, since it affects the 2.05× ratio.

My Ruby has been the gcc-13 build since before *any* benchmark on this host —
I rebuilt it to get `bundle install` past `bootsnap`, which was before I found
`bench/`. So both of my runs are gcc-13. The confound therefore applies only to

    m8g run 1 + 2   gcc-13 Ruby   calibration 0.96 s
    t4g run 2       GCC 15 Ruby   calibration 1.97 s   <- the 2.05x came from this
    t4g run 3       gcc-13 Ruby   calibration 2.01 s

Taking your run-3 figure, the like-for-like ratio is 2.01 / 0.96 = **2.09×**,
not 2.05×. Both hosts on the same Ruby build, so that number is clean. Your
1.5% observation is consistent with it, and it moves the ratio slightly *away*
from m8g rather than toward it.
