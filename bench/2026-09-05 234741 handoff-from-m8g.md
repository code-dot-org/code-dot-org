## 4. Proposed next steps

Ranked by value, with a suggested owner. Everything here is verified on both
hosts unless marked otherwise. Push back on any of it — particularly the split,
since you know your host's state better than I do.

**A. One real code bug, one line.** `lib/cdo/aws/s3.rb:96` calls
`Cdo::LocalDevelopment.populate_local_s3_bucket` but the file never requires
`cdo/local_development`. Loading only `cdo/aws/s3` leaves the constant
undefined, so `download_from_bucket` raises `NameError` whenever
`CDO.aws_s3_emulated` is true — which is the configuration `docker/developers`
tells you to use. Verified in isolation:

    ruby -e 'require "./deployment"; require "cdo/aws/s3"; Cdo::LocalDevelopment'
    => NameError: uninitialized constant Cdo::LocalDevelopment
    # with require "cdo/local_development" added: resolves

This is also part of `shared/test_aws_s3_integration.rb`'s failure, which we
have both been filing under "no AWS credentials". That is only half true: the
VCR cassette misses are credentials, the `NameError` is this bug.

*I will take this one* unless you have already. It is a one-line fix plus a
regression test, and I have the reproduction.

**B. `docker/developers` is broken as documented.** Four defects, all
independently confirmed:

1. `README.md:51` tells you to run `docker compose run all-services`. No such
   service exists anywhere in the repo.
2. That directory has no default compose file, so every documented
   `docker compose` invocation there fails to find a project.
3. `.env` lines 3 and 6 use YAML `KEY: value` where dotenv requires
   `KEY=VALUE`, so `REDIS_NATIVE_PORT` is never set and `dashboard-services`
   prints `redis_url: redis://localhost:/0`.
4. `docker-compose.dashboard.yml` tells you to write
   `db_endpoint_writer: 127.0.0.1:3306` into `locals.yml`, but the code wants a
   bare host plus a separate `_port` key. You hit
   `URI::InvalidComponentError`; I hit a silently wrong `bin/mysql-client-admin`.

A new developer following that directory's README cannot get to a running
stack. *Suggest you take this* — your override file already encodes the right
shape for most of it.

**C. `install_npm` is destructive.** `lib/cdo/rake_utils.rb:244` early-returns
only if `which npm` succeeds. Without nvm on `PATH`, `rake install` runs
`sudo apt-get install -y nodejs npm`, force-symlinks `/usr/bin/node`, and then
`npm install -g npm@2.9.1`. I caught it mid-apt. Any non-interactive shell — a
cron job, an IDE terminal, CI — is exposed, and its own comment calls the guard
a temporary workaround. Fix is to detect an nvm-managed node rather than to
shell out to apt on a developer machine. *Unowned; low effort, needs a
maintainer's opinion on the intended behaviour.*

**D. Documentation.** SETUP.md's stale version table and missing `libyaml-dev`;
`pdftk` and `chromium-browser` unavailable on arm64; TESTING.md documenting a
pegasus suite that contains no tests and warning about a `PDFMergerTest` that
does not exist. Small, uncontroversial, and each one costs the next person
time. *Whoever gets to it; probably one PR with B.*

**E. The wedge, unresolved.** `RAILS_ENV=test bundle exec rails test` over the
whole tree does not finish. You measured 64 tests in 63 minutes then no
progress; I killed one at 90 minutes with no output. Two instance families,
two independently built environments. It is the headline command in TESTING.md
and it does not work, and neither of us knows why — loading all 698 test files
into one process is the trigger, but that is a description, not a cause.

*I think this deserves an issue even if nobody chases it now*, because right
now the only record is a comment in `bench-cdo-tests.sh`. If either of us does
chase it, the cheap first experiment is bisecting the directory list to find
whether one directory wedges it or whether it is cumulative.

**F. Not shared work, but flagging it.** My MySQL still binds `0.0.0.0:3306`
with root/password; I am applying your loopback binding next. If your host is
still on `0.0.0.0` it is worth doing regardless of the benchmark.
