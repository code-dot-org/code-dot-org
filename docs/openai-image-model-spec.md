# Adding an OpenAI image model to Sprite Lab 2

Status: reviewed and accepted; implementation in progress. See
[Implementation status](#7-implementation-status) at the end for what has
landed. Sections 1-3 have been corrected against the gateway worker source,
which was not available when the first draft was written.

Scope: describe how image generation works today, from the Sprite Lab 2
dialog through the AI Gateway to Google's image model; assess what it
would take to offer OpenAI's image model alongside it; and lay out the
implementation steps. Sprite Lab 2 is the playtest surface, but the
gateway and model-id work below is shared by every caller.

---

## 1. Current state

### 1.1 Components

| Layer | Location |
| --- | --- |
| Sprite Lab 2 image dialog | `apps/src/p5lab/spritelab/lab2/views/` |
| Sprite Lab 2 image pipeline | `apps/src/p5lab/spritelab/lab2/ai/images/` |
| AI SDK-shaped gateway client | `apps/src/aiGateway/` |
| Wire contract + snapshots | `apps/src/aiGateway/contract/` |
| Token minting | `dashboard/app/controllers/ai_gateway_auth_controller.rb` |
| Authorization rules | `dashboard/app/models/concerns/user/ai_accessible.rb` |
| Model ids | `lib/cdo/shared_constants.rb` |
| Gateway worker | **not in this repo** — see §1.8 |

### 1.2 The request path

A generation from the Sprite Lab 2 Images tab travels:

1. `GenerateImageView` collects prompt, image type, style, randomness
   source and temperature, then calls `generateImage()`
   (`ai/images/imageGeneration.ts`).
2. `generateImage()` appends a style clause and a type-specific
   composition clause to the user's prompt, rolls a 31-bit seed if the
   caller did not supply one, and calls `generateText()` from
   `@cdo/apps/aiGateway` with `model: getImageModel()`.
3. `generateTextThroughGateway()` (`aiGateway/generateText.ts`):
   - reduces the AI SDK model object to its `modelId` string,
   - serializes any structured-output schema (unused on this path),
   - `POST /ai_gateway/access_token` to Rails, which returns a signed
     RS256 JWT valid for one minute and the Turnstile enforcement mode,
   - solves a Turnstile challenge if the mode demands one,
   - `POST https://ai-gateway.code.org` with the JSON body
     `{...options, model: <string>, token: <jwt>}` and the headers
     `X-AI-Gateway-Schema-Version: 1`, optional
     `x-ai-gateway-phase`, and the Turnstile headers. The call goes out
     without the Rails authenticity token — the gateway is a different
     origin and authenticates on the JWT alone.
   - validates the response against
     `GatewayGenerateTextResponseV1Schema` (a mismatch is reported to
     Sentry and, outside development, tolerated),
   - rehydrates it into an AI SDK `GenerateTextResult`: base64 file
     payloads become `Uint8Array`, the response timestamp becomes a
     `Date`.
   - The whole call is wrapped in a Sentry span, `ai-gateway.generateText`.
4. Back in `generateImage()`, the first `image/*` entry in `result.files`
   is the generated image. Everything after that is local canvas work
   (§1.5).

Sprite Lab 2 passes no `phase`, so its requests carry no
`x-ai-gateway-phase` header. It also does not run the aichat moderation
pipeline — `askSpriteLabAi.ts` states the rule for the lab explicitly:
prompt safety is whatever the gateway enforces.

### 1.3 The wire contract

`apps/src/aiGateway/contract/gatewaySchemas.ts` is the client's half of
the contract. Two operations exist:

- `POST https://ai-gateway.code.org` — generateText. JSON in, JSON out.
- `POST https://ai-gateway.code.org/transcribe` — transcription.
  `FormData` in, JSON out.

Each has a request and a response schema, versioned in a
`Record<number, ZodTypeAny>` map, with a committed JSON snapshot under
`contract/schemaSnapshots/`. `schemaChangeDetector.ts` classifies a
diff against the snapshot as `HARD_BREAKING`, `UNKNOWN_NARROWING` or
`ADDITIVE`, and the tests in
`apps/test/unit/aiGateway/contract/` fail on an unreviewed break.
`CURRENT_SCHEMA_VERSION` is pinned at `'1'` and is documented as needing
to move in lockstep with `CURRENT_VERSION` in the worker's
`src/contract/version.ts`.

The generateText response carries `text`, `finishReason`, `usage`,
`output`, `warnings`, `files[] = {mediaType, base64}` and a `response`
metadata block whose `body` is the raw provider payload. Image
generation uses only `files` and, in AI Chat Lab, `response.body` for
Gemini's non-standard moderation reporting.

### 1.4 Model selection today

Model ids live in `AI_CHAT_MODEL_IDS` in `lib/cdo/shared_constants.rb`
and reach the frontend as `AiChatModelIds` in
`apps/generated-scripts/sharedConstants.ts`, regenerated by the apps
build. Two derived lists matter:

- `AI_CHAT_GEMINI_MODEL_IDS` — routing: which provider serves a model.
- `AI_CHAT_US_ONLY_MODEL_IDS` — currently aliased to the Gemini list;
  access, not routing.

Sprite Lab 2 does not select a model at runtime. `getImageModel()` in
`ai/images/modelHelpers.ts` returns exactly one thing:

```ts
googleProvider(AiChatModelIds.GEMINI_2_5_FLASH_IMAGE)
```

with an empty API key, because the key is injected by the gateway. The
same file pins `MODEL_OUTPUT_PX = 1024` and `ASSUMED_BLOCK = 16` and
says in a comment that these are the image model's output policy, kept
beside the model id so a model swap forces them into view. That comment
is the seam this work has to widen.

AI Chat Lab, by contrast, does have a model picker: `modelHelpers.ts`
under `apps/src/aichat/api/client/helpers/` builds a map from every
Gemini id plus `gpt-4o-mini` to an AI SDK `LanguageModel`, and
`apps/static/aichat/modelDescriptions.json` supplies the descriptions
the picker shows. An id with no description entry is filtered out of
that picker, so adding an id does not by itself expose it in AI Chat Lab.

### 1.5 What Sprite Lab 2 does with the bytes

The model returns roughly a 1024x1024 image. `imageGeneration.ts` then:

- **sprite** and **block**: the prompt asked for the subject on a flat
  key color that appears nowhere on the subject;
  `removeBackground()` floods that color to transparency (soft matting
  for smooth style, hard for pixel). Blocks are additionally cropped to
  content so grid copies tile.
- **background**: flattened onto an opaque ground.
  A smooth-style JPEG background short-circuits the whole canvas path
  and is stored as-is.
- **pixel** style, any type: `normalizePixelArtBlob()` detects the block
  grid the prompt asked for, downsamples to true logical resolution and
  re-upscales nearest-neighbor. The detected physical-pixels-per-art-pixel
  is recorded as `pixelGridSize` so the pixel editor never re-detects.

The result is uploaded to the project's asset bucket (or, in level edit
mode, to the level's starter assets) and recorded on the animation
together with `ImageGenerationMetadata`:

```ts
{prompt, imageType, style, seed, temperature?, editedPrevious?}
```

That record is what makes "use same seed" and "use previous image"
possible on a later visit. **It does not record which model made the
image.** For a two-model playtest that is a gap, not a detail (§3.5).

### 1.6 Authorization and region gating

`AiGatewayAuthController#get_access_token` checks
`can_access_aichat_chat_completion?(clientType, currentLevelId)`. Sprite
Lab 2 registers itself with `AichatContextManager` as
`AI_CHAT_CLIENT_TYPES[:FLOW_LAB]`, and `trust_chat_client?` returns
true for `FLOW_LAB`, so any signed-in user clears that check.

The second check is the interesting one:

```ruby
if current_user.us_only_aichat_models_disabled?
  return render status: :forbidden, ...
end
```

with the comment: the gateway serves Gemini for generation, the minted
token is *not bound to a model*, so a token issued for one model can be
replayed against another; refuse to mint at all rather than trust a
client-supplied model id we cannot enforce later.

Two consequences for this work:

- International users get no image generation today, and adding a model
  that is not US-only does not change that, because the refusal is
  per-user, not per-model.
- Conversely, if we did relax the refusal for OpenAI, a token minted for
  an international user could be replayed against Gemini. Relaxing it
  safely requires binding the model — or an allowed-model set — into the
  JWT and enforcing it in the worker.

### 1.7 Moderation

Sprite Lab 2 runs none client-side. AI Chat Lab's
`safetyHelpers.ts` gates text and images with a Gemini 2.5 Flash judge
plus `moderateImage`, and `generateChatResponse` reads Gemini's
`finishReason` out of `response.body.candidates[0]` to distinguish a
content-filter block from a failure. None of that is on the Sprite Lab 2
path.

### 1.8 The gateway worker

Not in this repo: it is `code-dot-org/ai-gateway`, a Cloudflare Worker.
What it does, from its source:

- `src/index.ts` validates the RS256 JWT (Rails holds the private key in
  `CDO.ai_gateway_auth_key`) and, when the JWT's
  `turnstile_enforcement_mode` claim says so, the Turnstile token. Only
  then does it dispatch on `url.pathname`.
- `POST /` — `src/generateTextHandler.ts`. **Google Vertex only.** It
  builds a `createVertex` client pointed at Cloudflare's AI Gateway with
  a service-account BYOK header, and falls back from standard to
  priority PayGo on a 429 for the models Google documents as supporting
  it. There is no model-to-provider table: a model string containing
  `gemini` is used as-is, and anything else **defaults to
  `gemini-2.5-flash`**.
- `POST /transcribe` — `src/transcriptionHandler.ts`. OpenAI, via
  `createOpenAI` with `env.OPENAI_API_KEY`, hardcoded to `whisper-1`.
- `src/contract/serializers.ts` turns an SDK result into the wire shape,
  dispatching on the schema version; `src/contract/version.ts` holds
  `SUPPORTED_VERSIONS` and `CURRENT_VERSION`, both `'1'`.
- The contract itself is consumed as a **sparse git submodule** pinned to
  a code-dot-org `staging` commit, exposed to the worker as `@contract/*`.

Two corrections to the first draft, both material:

- **The gateway does not serve `gpt-4o-mini`.** `shouldUseAiGateway`
  returns false for it, so AI Chat Lab's OpenAI traffic goes through
  Rails, not here. What the worker does already have is an OpenAI API key
  and a Cloudflare AI Gateway OpenAI base URL, both in the transcription
  handler — which is the part that made this work cheap.
- **The contract must move first.** Because the worker reads the schemas
  out of a submodule pinned to code-dot-org `staging`, the worker cannot
  compile against a schema that has not merged there. The first draft had
  the worker PR landing ahead of the client; the real order is: contract
  schemas to code-dot-org `staging` (inert, nothing calls them) → bump
  the submodule and add the route in the worker → deploy the worker →
  ship the client behavior.

One thing to know before load-testing: `wrangler.jsonc` configures a
per-user rate limit of 50 requests per 60 seconds, shared across every
route.

## 2. What OpenAI offers, and how it reaches the AI SDK

`apps/package.json` pins `ai@^6.0.73` and `@ai-sdk/openai@^3.0.26`; both
are installed. Reading the installed provider:

- `openai.image(modelId)` accepts `'dall-e-3' | 'dall-e-2' |
  'gpt-image-1' | 'gpt-image-1-mini' | 'gpt-image-1.5'` (and any
  string).
- `ai`'s `generateImage({model, prompt, n, size, aspectRatio, seed,
  providerOptions, ...})` is the call surface, where
  `prompt: string | {images, text?, mask?}`.
- The provider posts to `/images/generations`, or to `/images/edits`
  when the prompt carries input images. `gpt-image-1*` always returns
  base64 (`b64_json`); no URL fetch step.
- `providerOptions.openai` is spread verbatim into the request body,
  which is how `background`, `output_format`, `quality` and `moderation`
  reach the API.
- `seed` is explicitly rejected: the model emits
  `{type: 'unsupported', feature: 'seed'}` and ignores it.
- `aspectRatio` is likewise unsupported; use `size`
  (`1024x1024`, `1024x1536`, `1536x1024`, `auto`).

There is a second route — the Responses API with the provider-defined
`openai.tools.imageGeneration()` tool, reachable from `generateText`.
It is rejected below (§3.3).

## 3. Feasibility

### 3.1 The shape mismatch

Sprite Lab 2 reaches Google's image model through `generateText`
because Gemini 2.5 Flash Image is a *language* model that happens to
emit image parts, and the AI SDK surfaces those in `result.files`.
OpenAI's image models are not language models. They live behind a
different AI SDK call (`generateImage`), a different provider interface
(`ImageModelV3`), and a different HTTP endpoint. No amount of model-id
substitution bridges that: `getImageModel()` cannot simply start
returning `openaiProvider.image('gpt-image-1')`, because
`generateText()` will not accept an `ImageModel`.

So the question is not "can the gateway serve OpenAI" — it already
serves `gpt-4o-mini` to AI Chat Lab, so the key and the routing table
exist. The question is which call shape carries an image request.

### 3.2 Option A — a `generateImage` gateway operation (recommended)

Add a third operation, `POST https://ai-gateway.code.org/generateImage`,
mirroring what `/transcribe` already establishes: same token, same
Turnstile headers, same schema-version header, its own request and
response schema pair.

Request (v1):

```
{token, model, prompt, n?, size?, seed?, providerOptions?,
 images?: [{base64, mediaType}], mask?: {base64, mediaType}}
```

Response (v1):

```
{images: [{base64, mediaType}], warnings?, usage?, response?}
```

Worker side: recognize the image model ids, construct the provider's
image model, call `generateImage`, return the result. It is the same
work `/transcribe` already does for a non-language model.

Client side: `apps/src/aiGateway/generateImage.ts` alongside
`generateText.ts` and `transcribe.ts`, exported from `index.ts`, with
the same access-token → Turnstile → post → validate → rehydrate
sequence and its own Sentry span.

Cost: one new endpoint in two repos, two new schemas plus snapshots.
Benefit: the contract says what is actually happening; the Google path
is untouched; and any future image model (including a Gemini image
model addressed as an image model rather than a chat model) drops into
the same slot.

### 3.3 Option B — overload `generateText` in the worker

Keep the client calling `generateText` and have the worker notice an
OpenAI image id, call `generateImage` internally, and pack the result
into `files[]`.

This is the smallest diff — `imageGeneration.ts` would need almost no
change, since it already reads only `files`. It is still the wrong
answer: `messages`, `temperature`, `seed` and `output` are all
meaningless on that path and would be silently dropped, the response's
`finishReason` would be fabricated, and the schema would describe a
request the server does not honor. The next person to read the contract
would be misled. Reject.

### 3.4 Option C — Responses API `image_generation` tool

`generateText` with `openai.responses(...)` and
`openai.tools.imageGeneration({background, size, quality,
outputFormat, inputFidelity, ...})` does produce images from a
`generateText` call, and does accept multimodal input naturally.

Two problems. First, the tool's output is typed `{result: string}` — a
base64 image delivered as a *tool result*, not in `result.files`, so
the gateway response schema would still need widening and the client
would still need a new read path. Second, it puts a chat model in front
of every image request: more latency, more cost, and a second model
free to rewrite the prompt we carefully constructed in §1.5. Reject for
this use, though it is the right tool if we later want conversational
image editing.

### 3.5 Capability differences that reach the UI

These are the real cost of the feature, and they are all in the dialog,
not the gateway.

| Control | Gemini 2.5 Flash Image | gpt-image-1 |
| --- | --- | --- |
| Temperature slider | honored | no such parameter |
| "Use same seed" | honored | rejected by the provider |
| "Use previous image" | image part in the message | `/images/edits`, supported |
| Transparent background | prompted for, then keyed out locally | `background: 'transparent'` native |
| Output size | ~1024 square | `1024x1024` / `1024x1536` / `1536x1024` |
| Multiple candidates | one per call | `n` up to 10 |

Consequences:

- **Temperature and seed must disable themselves** when the OpenAI
  model is selected. Leaving a live slider that silently does nothing is
  worse than hiding it. `GenerateImageView` already disables the seed
  radio when there is no recorded seed; the same mechanism extends to
  "the selected model cannot seed".
- **Native transparency may make `removeBackground()` unnecessary** for
  sprites and blocks on the OpenAI path — and the flat-key-color clause
  in the prompt with it. That is worth testing during the playtest
  rather than deciding now: keying is lossy, and a native alpha channel
  would be strictly better if the model honors it. Block cropping
  (`cropToContent`) is still needed either way. Verify
  `background: 'transparent'` against the live API before relying on it;
  the provider spreads `providerOptions.openai` into the body without
  validating it.
- **`ImageGenerationMetadata` must record the model.** Without it, a
  playtest cannot tell which model produced an image, "use same seed"
  cannot know whether the recorded seed is replayable, and a
  regeneration cannot default to the model that made the current image.
  This is a required field, not a nice-to-have.
- **Per-image cost differs materially** between the two models. Get the
  current numbers before the playtest opens to students; a
  classroom-scale rollout is not the place to discover a 10x.

### 3.6 Region gating

Recommendation for the playtest: leave
`us_only_aichat_models_disabled?` and the blanket refusal exactly as
they are. `gpt-image-1` must **not** be added to
`AI_CHAT_GEMINI_MODEL_IDS` or `AI_CHAT_US_ONLY_MODEL_IDS`, but that has
no effect while the controller refuses per user rather than per model.
International users keep the behavior they have today: no image
generation. No regression, no new attack surface.

If serving international users from the OpenAI model becomes a goal, it
is a separate piece of work: put the permitted model set in the JWT and
enforce it in the worker, then narrow the controller's refusal to the
models the user actually cannot use. Do not do this as a side effect of
the playtest.

### 3.7 Verdict

Feasible. The worker already holds an OpenAI key and an OpenAI base URL
(for whisper-1), and the AI SDK versions in both repos already support
OpenAI image generation including edits. The work splits as:

- **gateway repo**: one new route with its own handler, serializer and
  model allowlist.
- **this repo**: one new gateway client module, two schemas, one model
  id, a model registry in Sprite Lab 2, a capability-aware dialog, and
  a metadata field.

Nothing here requires a change to the Rails token endpoint, the
Turnstile design, the schema version, or the Google path. Note that the
generateText handler defaults an unrecognized model to
`gemini-2.5-flash` — which is exactly why `/generateImage` refuses an
id outside its allowlist instead of defaulting: a wrong image model
would silently draw the wrong thing.

## 4. Implementation steps

Ordered so each step is independently reviewable, and so the client can
be built and unit-tested before the worker exists.

**Step 0 — agree the contract.** Settle §3.2's request/response shape
with whoever owns the gateway repo, and settle whether
`CURRENT_SCHEMA_VERSION` stays at `1` (a new endpoint with its own v1
schemas does not obviously bump the shared header). Blocking; everything
else assumes an answer.

**Step 1 — model id.** Add to `AI_CHAT_MODEL_IDS` in
`lib/cdo/shared_constants.rb`:

```ruby
OPENAI_IMAGE: "gpt-image-1",
```

Add it to neither `AI_CHAT_GEMINI_MODEL_IDS` nor
`AI_CHAT_US_ONLY_MODEL_IDS`, and give it no entry in
`apps/static/aichat/modelDescriptions.json` — that keeps it out of AI
Chat Lab's picker. `apps/generated-scripts/sharedConstants.ts` is
regenerated by the apps build.

**Step 2 — gateway client.** Add
`apps/src/aiGateway/contract/gatewaySchemas.ts` entries
`GatewayGenerateImageRequestV1Schema` /
`GatewayGenerateImageResponseV1Schema`, register them in
`ALL_GATEWAY_SCHEMA_GROUPS`, and run the snapshot updater
(`yarn update-ai-gateway-schema-snapshots` in `apps/`).
Add `apps/src/aiGateway/generateImage.ts` following
`transcribe.ts` — access token, Turnstile, POST, `safeParse`, rehydrate
base64 to `Uint8Array`, Sentry span named `ai-gateway.generateImage`.
Export it from `index.ts`.

**Step 3 — worker.** In the gateway repo: route `/generateImage`,
validate the token and Turnstile exactly as the other routes do, map
`gpt-image-1` to `openai.image('gpt-image-1')` with the injected key,
call `generateImage`, and return the agreed response. Deploy behind
whatever staging path that repo uses.

**Step 4 — a model registry in Sprite Lab 2.** Rewrite
`ai/images/modelHelpers.ts` around a table rather than a single
function. Roughly:

```ts
interface ImageModelSpec {
  id: string;
  label: string;              // shown in the dialog
  transport: 'generateText' | 'generateImage';
  outputPx: number;           // replaces the bare MODEL_OUTPUT_PX
  supportsSeed: boolean;
  supportsTemperature: boolean;
  supportsEdit: boolean;
  nativeTransparency: boolean;
}
```

with `getImageModelSpec(id)` and a `DEFAULT_IMAGE_MODEL_ID`. Keep
`MODEL_OUTPUT_PX` and `ASSUMED_BLOCK` exported for existing callers
(`GenerateImagePane`, `removeBackground`) until every one is on the
per-model value; `ASSUMED_BLOCK` is a prompt-and-detection contract and
stays shared unless a model forces otherwise.

**Step 5 — branch the pipeline.** In `ai/images/imageGeneration.ts`:

- `GenerateImageOptions` gains `modelId?: string`.
- Resolve the spec, then dispatch: the existing `generateText` body for
  the Gemini transport; a new `generateImage` body for the OpenAI one,
  translating `inputImageDataURI` into the `{images: [...], text}`
  prompt form and mapping the style/type clauses onto
  `providerOptions.openai` (`background: 'transparent'` for sprite and
  block, if it survives testing) plus `size`.
- Drop `seed` and `temperature` from the request when the spec says the
  model does not take them; keep rolling and recording a seed only where
  it is replayable.
- Record `model` in the returned `ImageGenerationMetadata`.
- The post-processing tail (`removeBackground`, `cropToContent`,
  `flattenOntoGround`, `normalizeIfPixelArt`) stays shared, gated on
  `spec.nativeTransparency` for the keying step.

**Step 6 — metadata.** Add `model?: string` to
`ImageGenerationMetadata` in `ai/images/types.ts`. Absent means the
Gemini model, so existing projects keep working without a migration.
Nothing else in the animation record changes.

**Step 7 — the dialog.** In `GenerateImageView`:

- Add a `Model` fieldset beside `Type` and `Style`, built from the
  registry, defaulting to the model recorded on the image being
  regenerated, else `DEFAULT_IMAGE_MODEL_ID`.
- Gate its visibility on a new experiment, e.g.
  `experiments.SPRITELAB_IMAGE_MODEL_PICKER = 'spritelab-image-model'`,
  read with `isEnabledAllowingQueryString`. That gives the playtest both
  requested affordances at once: `?spritelab-image-model=1` on the level
  URL turns the picker on for that page load, and
  `?enableExperiments=spritelab-image-model` persists it for the
  session's 12-hour experiment lifespan. With the experiment off, the
  dialog is exactly what it is today.
- Disable the temperature fieldset and the "use same seed" radio when
  the selected model does not support them, and say why in the label —
  a disabled control with no explanation reads as a bug.
- Reset `source` to `'new'` if the selected model makes the current
  choice impossible.

**Step 8 — accessibility pass.** The new fieldset is a radio group in a
modal: legend, `aria-describedby` on the disabled controls carrying the
reason, and focus order that puts Model before the controls it governs.
Run the `accessibility` skill's checklist over the dialog; it is a
student-facing control.

## 5. Testing

**Unit, frontend** (`cd apps && yarn test:unit <file>`):

- `test/unit/p5lab/spritelab/lab2/imageGenerationTest.ts` — extend. It
  mocks `@cdo/apps/aiGateway`'s `generateText`; add a mock for
  `generateImage` and assert per model: which transport was called, that
  seed and temperature are omitted for OpenAI, that
  `inputImageDataURI` becomes an `images` prompt for OpenAI and an image
  message part for Gemini, and that `generation.model` is recorded.
- `test/unit/aiGateway/contract/` — the snapshot and breaking-change
  tests cover the new schemas once registered.
- A new `test/unit/aiGateway/generateImageTest.ts` mirroring the
  existing gateway client tests: token fetch, header set, schema
  mismatch reporting.

**Type and lint:** `yarn run typecheck` in `apps/`, then
`./tools/hooks/pre-commit` from the repo root.

**Ruby:** `AI_CHAT_MODEL_IDS` gains a key; run
`bundle exec spring testunit ./test/models/concerns/user/ai_accessible_test.rb`
and `./test/controllers/ai_gateway_auth_controller_test.rb` from
`dashboard/` to confirm the new id is not swept into the US-only list
and the controller is unchanged.

**Manual, cannot be done without the deployed worker:**

- Generate each of sprite, background and block, in each of smooth and
  pixel style, on each model, and compare. Pixel-art fidelity is the
  one most likely to differ: the Gemini path's whole
  `normalizePixelArtBlob` step assumes a model that draws uniform
  blocks when asked.
- Confirm `background: 'transparent'` actually produces alpha, and
  whether keying can be skipped.
- "Use previous image" on the OpenAI path, i.e. `/images/edits`.
- A signed-out user, and a user for whom
  `us_only_aichat_models_disabled?` is true, still get today's behavior.
- Latency and per-image cost, recorded, both models.

## 6. Open questions

Questions 1 and 2 of the original draft are settled: we own
`code-dot-org/ai-gateway`, and the schema version does not move for a new
endpoint — versions cover the whole API, but a route no existing client
calls ships at V1 with the version header where it is. What remains:

1. Which OpenAI model — `gpt-image-1`, `gpt-image-1-mini`, or
   `gpt-image-1.5`? All three are in the worker's allowlist; only
   `gpt-image-1` is wired into Sprite Lab 2's registry so far. The mini
   is the obvious candidate if per-image cost at classroom scale is the
   binding constraint.
2. Should the playtest expose the picker to students, or only to
   levelbuilders and teachers? The experiment flag can be set from a
   level URL, which reaches students.
3. Is a per-level default model wanted (a level property, the way
   `lockedImageType` works), or is the session-level experiment enough?
4. `background: 'transparent'` is sent but unverified against the live
   API — the one behavioral assumption in the client that only a real
   request can settle. See §7.
