# Availability gates

Five families of gate decide whether a capability is reachable: DCDO flags,
Gatekeeper rules, Experiments (including pilots), Rails environment and CDO
config, and feature modes. Each entry reads
`key | default | file:line | gates: <what> | role`. Mechanism notes at the end
of each section say who can flip that family and where.

### DCDO mechanism notes

DCDO ("Dynamic Config, Dynamo/Datastore-Overridden" in spirit — see class comment "A dynamic configuration module that allows us to update config settings without pushing new code") is defined in `lib/dynamic_config/dcdo.rb`, subclassing `DynamicConfigBase` and backed by a DynamoDB-cached key/value store (`EnvironmentAwareDynamicConfigHelper` + `DynamodbAdapter`/`JsonFileAdapter`/`MemoryAdapter` depending on environment); the global singleton `DCDO` is created once at load time. `DCDO.get(key, default)` reads a value (cached, refreshed periodically) and `DCDO.set(key, value)` writes it back to the datastore. In practice, admins change flags through the `/dcdo` admin page (`dashboard/app/views/dcdo/show.html.haml`, routed via `resource :dcdo` in `dashboard/config/routes.rb`, backed by `DcdoController#show`/`#update`), a simple form that lists every key currently in the store and lets an admin add or edit a key/value pair with an explicit data type (Integer/Float/Boolean/String/Array/Hash/etc); each update is logged to chat via `ChatClient.log`. `DcdoController` gates both actions on `authorize! :read, :reports`, and `Ability` (`dashboard/app/models/ability.rb`) denies `:reports` to everyone except users for whom `user.admin?` is true (which grants blanket `can :manage, :all`) — so only site admins can flip flags through the UI; anyone with Rails console/runner access can also call `DCDO.set` directly. Separately, `DCDO#frontend_config` (`lib/dynamic_config/dcdo.rb`) hand-picks a subset of DCDO keys and serializes them into a `<script data-dcdo>` tag on every page (`dashboard/app/views/layouts/application.html.haml:40`); client-side code reads that JSON via `apps/src/dcdo.js`, giving JS-only code the same `DCDO.get(key, default)` API against a page-load-time snapshot — a flag changed server-side only takes effect for a given browser tab after the next full page load (and is subject to whatever HTTP caching applies to that page).

### Gatekeeper mechanism notes

Gatekeeper (`lib/dynamic_config/gatekeeper.rb`, class `GatekeeperBase`, instantiated as the constant `Gatekeeper`) is a boolean feature-flag system built on the shared `DynamicConfigBase`/`DatastoreCache` machinery also used by DCDO, backed by a DynamoDB table (`CDO.gatekeeper_table_name`) via `EnvironmentAwareDynamicConfigHelper.create_datastore_cache`, with a local in-process cache refreshed periodically (and explicitly via `Gatekeeper.refresh`). Each feature name maps to a set of rules keyed by a JSON-serialized `where` condition hash (e.g. `{script_name: "..."}` or `{user_id: ...}`); `allows(feature, where:, default:)` checks the exact `where` match first, then the unconditional (`{}`) rule, then falls back to `default` (which itself defaults to `false` if the call site omits it — several call sites above rely on this implicit `false`). `disallows` is just `!allows(...)`. Values are changed in practice through the levelbuilder/admin-only `/gatekeeper` route (`GatekeeperController`, `dashboard/app/views/gatekeeper/show.html.haml`), which lets an authorized user view a feature's rules, `set` a new where/value pair, or `delete` a rule (each write is logged to chat via `ChatClient.log` and takes ~30s to propagate); access is gated by CanCanCan's `authorize! :read, :reports`, and since `:reports` is in the base `cannot` list, only users an `Ability` override grants it to (site admins, via `can :manage, :all`) can reach it. A related `/feature_mode` admin page (`FeatureModeController` + `FeatureModeManager`) bundles a handful of Gatekeeper (and DCDO) flags into named "modes" (e.g. an emergency/high-load mode) settable in one action. Outside the UI, flags can also be bulk-loaded from a YAML file via `GatekeeperLoader.load`/`apply_commands`, which calls `Gatekeeper.set` for each rule — useful for scripted or bulk changes rather than one-off admin clicks.

### Experiments mechanism notes

The Rails side is one STI hierarchy rooted at `Experiment` (dashboard/app/models/experiments/experiment.rb), backed by a single `experiments` table with a `type` discriminator column; the base class caches all `active` rows in a class variable (`@@experiments`, refreshed every `MAX_CACHE_AGE` seconds) so `Experiment.enabled?(user:, script:, experiment_name:)` and `Experiment.get_all_enabled` avoid a query on every check, and each subclass overrides `enabled?(user:)` to define its own opt-in rule. `UserBasedExperiment` (user_based_experiment.rb) is a straight percentage rollout: `user.id % 100` is compared against `min_user_id`/`max_user_id` (with `overflow_max_user_id` handling the wrap-around case), and the `percentage=` setter derives `min_user_id` from a SHA1 hash of the experiment name so a given experiment always claims the same slice of the ID space. `TeacherBasedExperiment` (teacher_based_experiment.rb) does the same modulus math but keyed on the *teacher's* user id (via `section.user_id % 100`), with optional `earliest_section_at`/`latest_section_at` bounds, so an entire section rides its teacher's bucket. `SingleSectionExperiment` (single_section_experiment.rb) is opted in by explicit `section_id` FK, capped at `MAX_COUNT = 2_000` rows for query performance, and `enabled?` checks whether the user teaches or studies in that section. `SingleUserExperiment` (single_user_experiment.rb) is the purely explicit case: `enabled?` is just `user.id == min_user_id`, i.e. one row per opted-in user, and this is the subclass every admin/self-serve opt-in path writes to. Concretely, a user gets into a `SingleUserExperiment` one of three ways: (1) an admin adds their email on `/admin/pilots/:pilot_name` (AdminPilotsController#add_to_pilot creates the row directly); (2) they click a "join pilot" link of the form `/experiments/set_single_user_experiment/:experiment_name`, which ExperimentsController only honors when a matching `Pilot` record has `allow_joining_via_url: true` (so pilots are admin-provisioned via the `pilots` table, but joining is user-initiated by URL, commonly from an email link); or (3) application code creates the row directly (e.g. `test_controller.rb` in test/dev environments). Self-service management lives at `/experiments`, which lists only the current user's own `SingleUserExperiment` rows and lets them `POST /experiments/leave/:experiment_name` (again gated by `Pilot#allow_joining_via_url`) — percentage- and section-based experiments are deliberately excluded from that page since the user never chose those. On the frontend, `apps/src/util/experiments.js` is a separate, client-only mechanism layered on top: `experiments.isEnabled(key)` checks (in order) a `_experiments` cookie mirrored at sign-in from the server-side enabled list, browser `localStorage` (written by `setEnabled`, with optional expiration), `window.appOptions.experiments` (server-injected per-page, see `levels_helper.rb:414` populating `@app_options[:experiments]` from `Experiment.get_all_enabled`), and `DCDO.get(key, false)` (an unrelated, ops-controlled feature-flag store); `?enableExperiments=a,b` / `?disableExperiments=a,b` query-string params persist a browser-local override, `?tempEnableExperiments=a,b` does the same with a 12-hour expiration, and `isEnabledAllowingQueryString` additionally treats a bare `?key=1` as a one-shot enable that is never persisted. So server-defined experiments (rollout %, section/teacher/user assignment) flow into the page via `appOptions.experiments` and the `_experiments` cookie, while purely client-side experiments are enabled ad hoc via query string or local storage and never touch the `experiments` database table at all.

### Env/config mechanism notes

Which Rails environment a deployed box runs as is set once, outside the app, by the deploy tooling: the `cookbooks/cdo-apps` Chef recipes (`libraries/cdo_apps.rb`, `recipes/build.rb`) write `RACK_ENV`/`RAILS_ENV` into the box's environment based on the stack it's building (production, staging, test, adhoc, levelbuilder), and Puma/Rails read that at boot. `rack_env?` (used throughout the controllers above) is a CDO helper that compares against this same value, plus recognizes `:adhoc` as its own pseudo-environment for developer-named adhoc boxes (`CDO.stack_name` distinguishes one adhoc from another). `aws/cloudformation` treats `RAILS_ENV` as a rake-task input (e.g. `RAILS_ENV=production` for IAM stack commands) rather than a runtime source — the CloudFormation stack itself doesn't set the app's env, the Chef run on the instance does. In short: environment identity is a deploy-time fact baked in by Chef/the stack-naming convention, and every gate above just reads that fact back via `Rails.env`/`rack_env?`/`rack_env`.

### Cross-reference: UserPermission overlap

`grep -rln "UserPermission" dashboard/app/controllers | grep -i -E "feature|gate|pilot"` returned no matches — no controller combines a direct `UserPermission` check with pilot/feature-mode gating. The overlap instead lives in models: `Unit#has_pilot_access?`, `Unit.has_any_pilot_access?`, `UnitGroup#has_pilot_access?`, `UnitGroup.has_any_pilot_access?`, and `Curriculum::AssignableCourse#course_assignable?` all short-circuit to `true` when `user.permission?(UserPermission::LEVELBUILDER)`, independent of the pilot experiment check — i.e. LEVELBUILDER permission is a universal bypass for every pilot-access gate found in this family. `feature_mode_controller.rb` gates via CanCan `authorize! :read, :reports` rather than `UserPermission` directly, but `:reports` is in the blanket `cannot :read` list for the base ability (dashboard/app/models/ability.rb:11-25), so only an ability override elsewhere (admin/staff role) grants it — that override chain is the other agent's territory.

### Pilot/feature-mode/CDO-config mechanism notes

A pilot is a row in the `pilots` table (name, display_name, allow_joining_via_url) managed entirely through `AdminPilotsController` at `/pilots` (admin-only, `require_admin` + `check_authorization`); the controller itself does no experiment-membership logic — it just creates `Pilot` rows and manages `SingleUserExperiment`/`Experiment` rows keyed by the pilot's `name` string, which is the actual gate consumed everywhere else via `User#has_pilot_experiment?` → `SingleUserExperiment.enabled?`. `Unit`/`UnitGroup` each carry their own `pilot_experiment` config value (from levelbuilder-authored course/unit config, not the `pilots` table) and delegate to that same primitive, so "is this pilot" and "is this course's pilot flag on" are two separate but converging mechanisms. `FeatureModeController` (routes at `/feature_mode`, admin-only via `:reports` ability) is a single-purpose ops lever: `show`/`update` read or bulk-write a whole slate of `Gatekeeper` features and `DCDO` keys at once, snapping the site between four canned postures (normal/scale/fallback/emergency) defined in `FeatureModeManager::MODE_SETTINGS_MAP` — it exists specifically for Hour-of-Code traffic spikes and database-overload emergencies, and both underlying stores (Gatekeeper, DCDO) are themselves runtime-toggleable without a deploy (per the other agent's DCDO/Gatekeeper family). `CDO.*` config booleans are a different mechanism entirely: they come from `config.yml.erb` (repo root, not `dashboard/config/` — that directory holds only infra config like `database.yml`/`cable.yml`) merged with a per-environment file (`config/development.yml.erb`, `config/production.yml.erb`, etc.) and a developer's local `locals.yml` override; because these are loaded at process boot into the `CDO` config object, changing one requires a restart in dev and a full deploy in production — there is no runtime toggle path for `CDO.*` the way there is for DCDO/Gatekeeper. A few (`default_hoc_mode`, `default_courses_show_ai`) are explicitly named as fallbacks superseded by same-named DCDO keys everywhere except `:test`, showing the two systems are meant to overlap deliberately at the config layer.
