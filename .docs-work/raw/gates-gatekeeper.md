### Gatekeeper mechanism notes

Gatekeeper (`lib/dynamic_config/gatekeeper.rb`, class `GatekeeperBase`, instantiated as the constant `Gatekeeper`) is a boolean feature-flag system built on the shared `DynamicConfigBase`/`DatastoreCache` machinery also used by DCDO, backed by a DynamoDB table (`CDO.gatekeeper_table_name`) via `EnvironmentAwareDynamicConfigHelper.create_datastore_cache`, with a local in-process cache refreshed periodically (and explicitly via `Gatekeeper.refresh`). Each feature name maps to a set of rules keyed by a JSON-serialized `where` condition hash (e.g. `{script_name: "..."}` or `{user_id: ...}`); `allows(feature, where:, default:)` checks the exact `where` match first, then the unconditional (`{}`) rule, then falls back to `default` (which itself defaults to `false` if the call site omits it — several call sites above rely on this implicit `false`). `disallows` is just `!allows(...)`. Values are changed in practice through the levelbuilder/admin-only `/gatekeeper` route (`GatekeeperController`, `dashboard/app/views/gatekeeper/show.html.haml`), which lets an authorized user view a feature's rules, `set` a new where/value pair, or `delete` a rule (each write is logged to chat via `ChatClient.log` and takes ~30s to propagate); access is gated by CanCanCan's `authorize! :read, :reports`, and since `:reports` is in the base `cannot` list, only users an `Ability` override grants it to (site admins, via `can :manage, :all`) can reach it. A related `/feature_mode` admin page (`FeatureModeController` + `FeatureModeManager`) bundles a handful of Gatekeeper (and DCDO) flags into named "modes" (e.g. an emergency/high-load mode) settable in one action. Outside the UI, flags can also be bulk-loaded from a YAML file via `GatekeeperLoader.load`/`apply_commands`, which calls `Gatekeeper.set` for each rule — useful for scripted or bulk changes rather than one-off admin clicks.
