### Experiments mechanism notes

The Rails side is one STI hierarchy rooted at `Experiment` (dashboard/app/models/experiments/experiment.rb), backed by a single `experiments` table with a `type` discriminator column; the base class caches all `active` rows in a class variable (`@@experiments`, refreshed every `MAX_CACHE_AGE` seconds) so `Experiment.enabled?(user:, script:, experiment_name:)` and `Experiment.get_all_enabled` avoid a query on every check, and each subclass overrides `enabled?(user:)` to define its own opt-in rule. `UserBasedExperiment` (user_based_experiment.rb) is a straight percentage rollout: `user.id % 100` is compared against `min_user_id`/`max_user_id` (with `overflow_max_user_id` handling the wrap-around case), and the `percentage=` setter derives `min_user_id` from a SHA1 hash of the experiment name so a given experiment always claims the same slice of the ID space. `TeacherBasedExperiment` (teacher_based_experiment.rb) does the same modulus math but keyed on the *teacher's* user id (via `section.user_id % 100`), with optional `earliest_section_at`/`latest_section_at` bounds, so an entire section rides its teacher's bucket. `SingleSectionExperiment` (single_section_experiment.rb) is opted in by explicit `section_id` FK, capped at `MAX_COUNT = 2_000` rows for query performance, and `enabled?` checks whether the user teaches or studies in that section. `SingleUserExperiment` (single_user_experiment.rb) is the purely explicit case: `enabled?` is just `user.id == min_user_id`, i.e. one row per opted-in user, and this is the subclass every admin/self-serve opt-in path writes to. Concretely, a user gets into a `SingleUserExperiment` one of three ways: (1) an admin adds their email on `/admin/pilots/:pilot_name` (AdminPilotsController#add_to_pilot creates the row directly); (2) they click a "join pilot" link of the form `/experiments/set_single_user_experiment/:experiment_name`, which ExperimentsController only honors when a matching `Pilot` record has `allow_joining_via_url: true` (so pilots are admin-provisioned via the `pilots` table, but joining is user-initiated by URL, commonly from an email link); or (3) application code creates the row directly (e.g. `test_controller.rb` in test/dev environments). Self-service management lives at `/experiments`, which lists only the current user's own `SingleUserExperiment` rows and lets them `POST /experiments/leave/:experiment_name` (again gated by `Pilot#allow_joining_via_url`) — percentage- and section-based experiments are deliberately excluded from that page since the user never chose those. On the frontend, `apps/src/util/experiments.js` is a separate, client-only mechanism layered on top: `experiments.isEnabled(key)` checks (in order) a `_experiments` cookie mirrored at sign-in from the server-side enabled list, browser `localStorage` (written by `setEnabled`, with optional expiration), `window.appOptions.experiments` (server-injected per-page, see `levels_helper.rb:414` populating `@app_options[:experiments]` from `Experiment.get_all_enabled`), and `DCDO.get(key, false)` (an unrelated, ops-controlled feature-flag store); `?enableExperiments=a,b` / `?disableExperiments=a,b` query-string params persist a browser-local override, `?tempEnableExperiments=a,b` does the same with a 12-hour expiration, and `isEnabledAllowingQueryString` additionally treats a bare `?key=1` as a one-shot enable that is never persisted. So server-defined experiments (rollout %, section/teacher/user assignment) flow into the page via `appOptions.experiments` and the `_experiments` cookie, while purely client-side experiments are enabled ad hoc via query string or local storage and never touch the `experiments` database table at all.
