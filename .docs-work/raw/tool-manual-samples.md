## Observed patterns

1. A trivial physical action (click, drag) almost never gets its own heading; it earns a heading only when it names a persistent UI region or feature (VS Code "Minimap", "Breadcrumbs"; Replit "Run button"; Scratch "Backpack") rather than the act of clicking it.
2. Multi-step *workflows* (create a branch, commit, turn in an assignment, change a theme) get numbered steps; single isolated actions (fold code, drag a tab, drag a block) get one prose sentence instead, no matter how "simple" the target feature is.
2b. The GitHub theme-settings page is the exception that proves the rule: a page whose ENTIRE content is one simple action is fully numbered because the numbering is the whole page, not a demotion of a small action inside a larger topic.
3. What a section adds beyond the click is consistently one or more of: the non-obvious state change afterward (Google Classroom: status becomes "Turned in"), a option/variant (Debugging's six breakpoint types), a shortcut binding, a limit ("Known limitations" on github.dev), or the underlying concept a beginner wouldn't infer from the UI alone (MDN's Layout view ties to CSS box model).
4. Screenshot use splits by source purpose: reference/concept pages (VS Code UI, MDN Inspector, Scratch UI) mix one full-UI orientation shot with several cropped single-control shots; task pages (Google Classroom, GitHub theme settings) use small inline icons or one cropped control per numbered step, never a full-window screenshot.
5. Every sampled page opens with orientation or definition before any instruction — none opens cold with step 1. VS Code and Scratch open by naming the mental model/layout; Apple and Replit open by stating what the whole tool/page is for; GitHub and Google task pages open with a one-sentence statement of what the reader will accomplish.
6. Conceptual/reference pages (VS Code User Interface, MDN Inspector, Scratch Wiki, Apple's Pages guide) separate reference from how-to by linking out to dedicated task pages rather than embedding procedures; task pages (GitHub theme settings, Google Classroom, Google Docs "how to") are almost entirely procedure, minimal concept.
7. Ratio of procedure-to-explanation is source-dependent, not action-dependent: MDN's Inspector tour is ~90% explanation/0 numbered steps; GitHub's theme page is ~90% numbered procedure; VS Code Basic Editing sits near 35/65 procedure/explanation by extraction estimate, mixing both modes across sections.
8. Sections that exist purely to catalog variants (VS Code's 6 breakpoint types, Scratch's 9 block categories implied by Block Palette, Google Docs' 3-step top-level flow) use a flat list or sub-heading ladder rather than prose paragraphs, so a reader can scan for "which variant do I need" without reading connective text.
9. No sampled page uses a numbered step for a single mouse click in isolation (no page has "1. Click Run." as its entire content) — a lone click is always folded into either a longer numbered sequence or a single prose sentence.
10. Pages aimed at a defined audience state the audience up front in sentence one (Google Classroom: "This article is for students"); pages aimed at a general/developer audience skip audience framing and start from the tool's identity instead.

## Where sites differ

- Numbering discipline: GitHub and Google (task-shaped pages) numbers almost everything with more than one action; VS Code and MDN (reference-shaped pages) numbers almost nothing, preferring prose or keyboard-shortcut notation even for multi-step sequences.
- Screenshot density: VS Code pages run 9-16 images per page (cropped-control heavy); GitHub pages run 1-5; Google Help pages run mostly small inline icons, not full screenshots; Apple's guide page uses 6 full-workflow images and zero cropped controls; MDN and Scratch sit in between with one full-UI shot plus several cropped panel shots.
- Where the "why" lives: VS Code and MDN put the non-obvious payoff inside the same section as the action; Google Help and GitHub task pages put it as a short trailing sentence after the numbered steps ("the status changes to Turned in"); Apple's top-level guide omits the payoff entirely and defers it to a linked sub-page.
- Audience address: Google Classroom names its audience explicitly ("This article is for students"); every other sampled page assumes a general or professional reader and never states an audience.
- Concept/procedure separation: VS Code and Apple keep concept pages free of embedded step-lists (link out instead); GitHub and Google keep task pages nearly free of concept explanation; MDN's Inspector tour and Scratch's UI page are concept-only with zero procedures at all.

## Closest proxies for a student app-building environment

1. **Scratch Wiki "User Interface"** — same audience (beginner students), same domain shape (block palette + canvas + stage), and it demonstrates the pattern most transferable to an App Lab manual: name each persistent UI region as its own heading, describe drag-onto-canvas behavior in one prose sentence with no numbered step, and reserve images for one full-UI orientation shot plus per-region crops.
2. **Replit "Editor & Tools"** — closest proxy for the mixed block/code, run-a-program shape: it gives "Run button" its own first-class heading (not just a step inside "how to run your project"), and separates layout/tool documentation from any single how-to task, which matches App Lab's need to document Run, Console/Debug console, and canvas/design-mode panes as named regions rather than as click instructions.
3. **VS Code "User Interface"** — closest proxy for the reference-vs-task separation App Lab would need at scale: it documents dozens of UI regions and behaviors (tabs, minimap, breadcrumbs) each as a named section with the non-obvious behavior stated inline, while linking multi-step workflows out to their own pages, which is the pattern for keeping a UI-region-heavy manual from reading as a click-list.
