### Cross-reference: UserPermission overlap

`grep -rln "UserPermission" dashboard/app/controllers | grep -i -E "feature|gate|pilot"` returned no matches — no controller combines a direct `UserPermission` check with pilot/feature-mode gating. The overlap instead lives in models: `Unit#has_pilot_access?`, `Unit.has_any_pilot_access?`, `UnitGroup#has_pilot_access?`, `UnitGroup.has_any_pilot_access?`, and `Curriculum::AssignableCourse#course_assignable?` all short-circuit to `true` when `user.permission?(UserPermission::LEVELBUILDER)`, independent of the pilot experiment check — i.e. LEVELBUILDER permission is a universal bypass for every pilot-access gate found in this family. `feature_mode_controller.rb` gates via CanCan `authorize! :read, :reports` rather than `UserPermission` directly, but `:reports` is in the blanket `cannot :read` list for the base ability (dashboard/app/models/ability.rb:11-25), so only an ability override elsewhere (admin/staff role) grants it — that override chain is the other agent's territory.

### Pilot/feature-mode/CDO-config mechanism notes

A pilot is a row in the `pilots` table (name, display_name, allow_joining_via_url) managed entirely through `AdminPilotsController` at `/pilots` (admin-only, `require_admin` + `check_authorization`); the controller itself does no experiment-membership logic — it just creates `Pilot` rows and manages `SingleUserExperiment`/`Experiment` rows keyed by the pilot's `name` string, which is the actual gate consumed everywhere else via `User#has_pilot_experiment?` → `SingleUserExperiment.enabled?`. `Unit`/`UnitGroup` each carry their own `pilot_experiment` config value (from levelbuilder-authored course/unit config, not the `pilots` table) and delegate to that same primitive, so "is this pilot" and "is this course's pilot flag on" are two separate but converging mechanisms. `FeatureModeController` (routes at `/feature_mode`, admin-only via `:reports` ability) is a single-purpose ops lever: `show`/`update` read or bulk-write a whole slate of `Gatekeeper` features and `DCDO` keys at once, snapping the site between four canned postures (normal/scale/fallback/emergency) defined in `FeatureModeManager::MODE_SETTINGS_MAP` — it exists specifically for Hour-of-Code traffic spikes and database-overload emergencies, and both underlying stores (Gatekeeper, DCDO) are themselves runtime-toggleable without a deploy (per the other agent's DCDO/Gatekeeper family). `CDO.*` config booleans are a different mechanism entirely: they come from `config.yml.erb` (repo root, not `dashboard/config/` — that directory holds only infra config like `database.yml`/`cable.yml`) merged with a per-environment file (`config/development.yml.erb`, `config/production.yml.erb`, etc.) and a developer's local `locals.yml` override; because these are loaded at process boot into the `CDO` config object, changing one requires a restart in dev and a full deploy in production — there is no runtime toggle path for `CDO.*` the way there is for DCDO/Gatekeeper. A few (`default_hoc_mode`, `default_courses_show_ai`) are explicitly named as fallbacks superseded by same-named DCDO keys everywhere except `:test`, showing the two systems are meant to overlap deliberately at the config layer.
