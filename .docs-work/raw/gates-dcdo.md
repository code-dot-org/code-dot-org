### DCDO mechanism notes

DCDO ("Dynamic Config, Dynamo/Datastore-Overridden" in spirit — see class comment "A dynamic configuration module that allows us to update config settings without pushing new code") is defined in `lib/dynamic_config/dcdo.rb`, subclassing `DynamicConfigBase` and backed by a DynamoDB-cached key/value store (`EnvironmentAwareDynamicConfigHelper` + `DynamodbAdapter`/`JsonFileAdapter`/`MemoryAdapter` depending on environment); the global singleton `DCDO` is created once at load time. `DCDO.get(key, default)` reads a value (cached, refreshed periodically) and `DCDO.set(key, value)` writes it back to the datastore. In practice, admins change flags through the `/dcdo` admin page (`dashboard/app/views/dcdo/show.html.haml`, routed via `resource :dcdo` in `dashboard/config/routes.rb`, backed by `DcdoController#show`/`#update`), a simple form that lists every key currently in the store and lets an admin add or edit a key/value pair with an explicit data type (Integer/Float/Boolean/String/Array/Hash/etc); each update is logged to chat via `ChatClient.log`. `DcdoController` gates both actions on `authorize! :read, :reports`, and `Ability` (`dashboard/app/models/ability.rb`) denies `:reports` to everyone except users for whom `user.admin?` is true (which grants blanket `can :manage, :all`) — so only site admins can flip flags through the UI; anyone with Rails console/runner access can also call `DCDO.set` directly. Separately, `DCDO#frontend_config` (`lib/dynamic_config/dcdo.rb`) hand-picks a subset of DCDO keys and serializes them into a `<script data-dcdo>` tag on every page (`dashboard/app/views/layouts/application.html.haml:40`); client-side code reads that JSON via `apps/src/dcdo.js`, giving JS-only code the same `DCDO.get(key, default)` API against a page-load-time snapshot — a flag changed server-side only takes effect for a given browser tab after the next full page load (and is subject to whatever HTTP caching applies to that page).
